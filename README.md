# kami-toolkit

Инструменты, которые берут на себя рутину при добавлении новой игры в
[KAMI](https://github.com/isJuhn/KAMI): найти в памяти RPCS3 значения камеры, найти к ним
устойчивую цепочку указателей и превратить результат в профиль, который KAMI загружает без
пересборки. Писались под inFAMOUS, но от игры не зависят.

```
camfind.py     поиск yaw/pitch камеры: снимки памяти, фильтрация, классификация, проверка записью
ptrscan.py     цепочки указателей от статических данных игры до найденного адреса; проверка после перезапуска
mkprofile.py   профиль KAMI из результатов; проверка профиля на живой игре; генерация класса C#
watch.py       наблюдение, запись в CSV, пробная запись, просмотр структуры, поиск значения, самопроверка
camrec.py      запись объекта камеры по сценарию (покой/ввод/ходьба/наклон) и поиск того, что включает автоцентровку
ps3elf.py      статический поиск по расшифрованному EBOOT: кто читает геймпад, кто пишет в поле, патчи RPCS3
gdbtrace.py    (эксперимент) какие из найденных инструкций реально выполняются - через GDB-заглушку RPCS3
rpcs3mem/      библиотека доступа к памяти RPCS3: процесс, PINE (IPC), дамп
ghidra_scripts/  четыре скрипта для Ghidra
cheatengine/   rpcs3_kami.lua для Cheat Engine
games/         известные сборки inFAMOUS (ID, хеши)
tests/         симулятор RPCS3 и автотесты
```

## Требования

Python 3.9+ и `numpy` (`py -3 -m pip install numpy`). Для автоматического вращения камеры в
Windows дополнительно `vgamepad` (ставит драйвер ViGEmBus). Windows или Linux.

RPCS3: актуальная сборка. Для имени игры и хеша включите IPC: **Manage → Network Services → IPC**
(в старых сборках Configuration → IPC), порт по умолчанию 28012.

## Три источника памяти

| источник | когда | особенности |
| --- | --- | --- |
| `process` (по умолчанию) | игра запущена | читает память процесса rpcs3 напрямую; быстро; работает одновременно с KAMI |
| `pine` | нет прав на чтение процесса | тот же IPC, что использует KAMI; медленно; **RPCS3 обслуживает одного клиента** - закройте KAMI |
| `dump` | офлайн | папка от **Utilities → Dump Guest Memory**; годится для `ptrscan` и `watch find/struct` |

Память PS3 лежит в процессе rpcs3 по адресу `0x300000000 + адрес` (зеркало без защиты страниц -
ещё на 4 ГиБ выше). База определяется автоматически; `--base` задаёт её вручную, её же печатает
RPCS3.log строкой `vm::g_base_addr`.

Первым делом проверьте доступ:

```
py -3 watch.py selftest --write
```

Команда находит процесс, базу, сверяет чтение через процесс и через PINE, а с `--write` проверяет
ещё и запись (переписывает 4 байта по `0x10000` их же значением: в игре ничего не меняется, но
видно, пускает ли система запись). Строка «N not allocated in the guest (PINE refuses, normal)» -
не ошибка: карта областей строится по отображению в память процесса и местами шире, чем то, что
игра реально выделила, а PINE на невыделенных страницах отвечает `IPC_FAIL`. Настоящая проблема
с IPC выглядит как `cannot connect` (IPC выключен) или `does not answer` (занят другим клиентом).
На Linux чтение чужого процесса требует root или `sysctl kernel.yama.ptrace_scope=0`.

## Основной путь

**1. Найти значения камеры.** Встаньте персонажем в спокойном месте (камера не двигается сама,
вокруг минимум движения) и запустите:

```
py -3 camfind.py                      # подсказки на экране, стик двигаете вы
py -3 camfind.py --stimulus vigem     # стик двигает виртуальный геймпад, руки не нужны
```

Что происходит: два снимка в покое (всё, что меняется само, отбрасывается), поворот вправо,
наклон вверх, затем серия шагов «покой / вправо / влево / вниз / вверх / шаг вперёд» уже только по
кандидатам, затем непрерывные трассы (полный оборот, до упора вверх и вниз) и проверка записью.
На выходе `camfind.json` и таблица: адрес, тип (`angle_rad`, `angle_deg`, `vec2`, `vec3`),
направление, пределы наклона, «липкость» и влияние.

Как читать результат. Нужное значение - то, которое игра сама интегрирует: после записи оно
**сохраняется** («липкий: да») и тянет за собой производные («влияние» - сколько других кандидатов
изменилось). Производные копии (сглаженный угол, вектор направления, матрицы) игра перезаписывает
на следующем кадре - для мыши они бесполезны.

Для `--stimulus vigem` в RPCS3 у игрока 1 должен стоять обработчик XInput, привязанный к
виртуальному геймпаду (отключите остальные XInput-геймпады или выберите нужный номер).
`--debug-addr 0x...` показывает, на каком шаге отсеялся конкретный адрес. `--no-poke` запрещает
запись в память.

Адреса уже известны (нашли вручную через `watch.py watch` / `poke`, или поиск прервался): фазы A и B
можно пропустить: `py -3 camfind.py --known-hor 0xАДРЕС [--known-vert 0xАДРЕС] -o camfind_cam.json`.
Берутся только эти слова (и два слова после горизонтального - вдруг это пара sin/cos или вектор),
затем идут обычные трассы (знаки, пределы наклона) и проверка записью. Получается тот самый
`camfind.json`, который нужен `mkprofile make`. Адреса в куче действуют только в текущем сеансе игры.

Поиск в состоянии, которое пропадает при уходе из окна игры (например, прицел: его надо держать зажатым):
`py -3 camfind.py --stimulus timed --no-walk -o camfind_aim.json`. Без Enter: после паузы
`--start-delay` (успеть перейти в игру и зажать прицел) консоль сама ведёт сценарий сигналами
(один сигнал - действуйте, два - стоп; на каждое действие `--prompt-time` секунд, перед трассой
`--lead`), окна консоли трогать не нужно. В прицеле игра пользуется другим объектом камеры, чем в
обычном режиме, поэтому его адреса ищутся отдельно и подключаются второй камерой с условием `when`.

Устойчивость. Всё, что при чтении как float32 оказывается NaN, inf или по модулю больше 1e5
(целые числа, указатели, мусор), превращается в NaN сразу при чтении и дальше не участвует ни в
вычитаниях, ни в приведении к целым, поэтому предупреждений NumPy нет. Ctrl+C безопасен в любой
момент: записанные при проверке значения возвращаются на место, найденное сохраняется. Сразу
после фазы C результат пишется в `camfind.json` с пометкой `partial` (без данных проверки записи):
если фаза D оборвётся, найденное не пропадёт; `mkprofile` такой файл прочитает, но предупредит, что
запись не проверялась.

Проверка записью (фаза D) идёт по кандидатам от лучшего к худшему (тип, согласие направления
в шагах и в трассе, близость кандидата другой оси: у мастер-значений они лежат в одном объекте),
оси чередуются. Печатается строка на каждого кандидата. Она кончается, когда на обеих осях найдены
держащиеся значения (`--poke-enough`, `--poke-after`), вышло время `--poke-budget` (300 с) или
проверено `--poke-count` (400 на ось). Влияние считается по небольшой выборке (`--poke-probe`), а не
по всем кандидатам: чтение 30 тысяч разбросанных слов занимает ~0,6 с. Если запись не проходит
(ошибка системы, значение не легло), это сразу печатается по-русски с вероятной причиной.

Если не двигается камера при записи в «липкий» адрес - это обычно производная копия, которую игра
пересчитывает; проверьте других кандидатов (`--poke-count 1000 --poke-budget 900 --poke-after 100`) и вручную:
`py -3 watch.py poke 0xАДРЕС 0.5 --add --wait 1.5`. Если ни один не держится - значение пишет код
игры каждый кадр: см. «Статический анализ» ниже.

Трассы (фаза C) читают таблицу кандидатов десятки раз в секунду; если одно чтение дольше
`--trace-ms` (250 мс), таблица сокращается до лучших кандидатов (чистые классы H/V, затем
согласованность направления, затем адрес), иначе трасса получилась бы в 1-2 отсчёта в секунду.

**2. Найти цепочку указателей.**

```
py -3 ptrscan.py find --target hor=0x30251BA8 --target vert=0x30251BC4 -o chains.json
```

Точную команду с адресами печатает `camfind`. Цепочки начинаются в записываемых сегментах самого
EBOOT (границы читаются из ELF-заголовка в памяти игры).

**3. Отсеять случайные цепочки.** Перезапустите игру (или хотя бы загрузите другую локацию) и:

```
py -3 ptrscan.py verify --chains chains.json
```

Без `--target` команда смотрит, куда сходятся цепочки, и оставляет согласованную группу; с
`--target hor=0x...` оставляет ведущие к указанному адресу. Повторите после ещё одного перезапуска,
пока список не перестанет сокращаться. Загрузка сохранения состояния (savestate) проверкой **не
является** - она восстанавливает ту же раскладку памяти.

**4. Собрать профиль и проверить его без KAMI.**

```
py -3 mkprofile.py make --camfind camfind.json --chains chains.json -o profiles\BCUS98119.json
py -3 mkprofile.py check --profile profiles\BCUS98119.json --nudge
```

`--nudge` двигает камеру так, как это сделал бы KAMI: вправо, обратно, вниз, обратно. Если не в ту
сторону - поменяйте `sign` у оси в JSON. Если `camfind` запускался при выключенном IPC или при
работающем KAMI, игру он не опознал: добавьте `--id BCUS98119` или `--hash PPU-...`.

**5. Отдать профиль KAMI.** Скопируйте файл в папку `profiles` рядом с `KAMI.exe` (нужна сборка
KAMI с поддержкой профилей, патч прилагается). Профиль перечитывается при каждом изменении.

**6. Когда всё устоялось** - превратить профиль в обычный класс игры для запроса на слияние:

```
py -3 mkprofile.py cs --profile profiles\BCUS98119.json --class InFamous -o InFamous.cs
```

## Вспомогательное

```
py -3 watch.py info                                   # игра, источник, карта памяти
py -3 watch.py watch --chains chains.json --csv log.csv
py -3 watch.py poke "[0x00A12340]+0x5C+0x118+0x1A8" 0.3 --add    # держится ли записанное
py -3 watch.py struct 0x30251BA8 --seconds 5          # что лежит рядом и что из этого меняется
py -3 watch.py find --u32 0x00812300-0x008123FF       # объекты по указателю на таблицу методов
```

Цепочка записывается так же, как в `DerefChain` у KAMI: `[база]+смещение+смещение+поле`.

Те же цепочки можно смотреть и менять в самом RPCS3, без сторонних программ:

```
py -3 ptrscan.py show --chains chains.json --rpcs3-cheats BCUS98119
```

Команда печатает строку для **Manage → Cheats**: скопируйте её и в окне читов выберите импорт из
буфера обмена. Каждая запись - это скрипт перенаправления RPCS3 (`[[[база]+смещение]+смещение]+поле`,
числа десятичные), поэтому она следует за объектом камеры после перезапуска.

## Игра сама возвращает камеру (автоцентровка)

Игра доворачивает камеру сама, пока персонаж идёт (за его спину и к среднему наклону), и это
складывается с мышью. Выключается принудительной записью в профиле (`writes`: например, обнулить
силу доворота или сбросить флаг), но сначала надо найти, что именно это решает в объекте камеры:

```
py -3 camrec.py record --spec "[0x00913964]+0x180" -o rec.npz     # KAMI выключен, камера - стиком
py -3 camrec.py analyze rec.npz
```

`record` ~100 раз в секунду читает весь объект камеры вокруг поля yaw, пока идёт сценарий (покой /
вращение камеры стиком / покой / ходьба вбок / покой / наклон вниз / ходьба вперёд / покой; смена фазы - звуковой
сигнал, список фаз печатается заранее; свой сценарий: `--script idle:6,input:6,...`).
`analyze` выделяет слова, поведение которых зависит от фазы, таймеры, растущие и сбрасывающиеся
при вводе, и флаги, которые переключаются; значение, которое при вводе обнуляется или меняется,
а в покое растёт, и есть кандидат на принудительную запись. Проверить такую запись можно командой
`py -3 watch.py hold --set "[база]+смещение" значение --seconds 20` (она делает то же, что `writes`).

Опыт с inFAMOUS (BCES00609), чем всё закончилось:

* Доворот при ходьбе считает игра каждый кадр от движения персонажа (в объекте камеры это
  скорости yaw/pitch, `+0x10` и `+0x14` от поля yaw; целевой наклон по умолчанию 0.35). Принудительная
  запись «флага» этого не отключает, но в сборке KAMI есть режим `"hold": true` в описании камеры
  (KAMI сам держит последний записанный угол); он убрал доворот. Этого режима нет в `kami-patch`
  из этой папки: он добавлен в сборке KAMI отдельно.
* Отскок («пружина») от стены - это отдельная последовательность игры: пока стик камеры не отклонён
  (мышь его не использует), столкновение запускает конечный автомат: `+0x11C` := 1, через 7 кадров
  `+0x28` := 2 (игра забирает камеру и разворачивает её за спину персонажа), затем втягивание камеры
  к персонажу. Слова хранят состояние между кадрами, поэтому частый сброс в 0 (`writes`:
  `[база]+0x29C` и `[база]+0x1A8`, оба `u32`, значение 0) срывает запуск, и отскока нет.
  Готовый профиль: `profiles/BCES00609_nowall.json`. (Запись `+0x28` := 1 вместо 0, как «стик
  держат», не годится: игра сама сбрасывает его каждый кадр, камера дёргается.)
* Прицел (BCES00609): в нём игра пользуется ДРУГИМ объектом камеры (обычный при этом замирает, его
  `+0x2F4` равно 3, `+0x28` = `FFFFFFFF`). Найден тем же `camfind` с зажатым прицелом на весь поиск
  (`--stimulus timed --no-walk`: сценарий идёт по таймеру и сигналам, Enter в консоли не нужен), yaw в
  `[0x0091398C]+0x234`, pitch в `+0x238` (у неё сторона вертикали противоположна обычной, предел
  наклона ±1.3906). Вторая камера в профиле с условием `when` `+0x2F4 == 3`.
* Прицельная камера хранит свой угол, и при выходе из прицела игра выравнивает по нему обычную, а мышь
  в обычном режиме его не обновляет: камера «прилипала» к точке первого прицела. Решение - зеркало
  (`mirror`) в обычной камере, которое пишет те же углы и в прицельную с поправками, ИЗМЕРЕННЫМИ по
  записи `watch.py watch --csv`, а не угаданными: `aim_yaw = follow_yaw + π`,
  `aim_pitch = −follow_pitch + 0.0629` (в пределах ±1.3906). Без поправки π камера при каждом входе в
  прицел разворачивалась на 180°.
* Итоговый профиль: `profiles/BCES00609_final.json` (копия того, что лежит в KAMI). Поля `hold`,
  `hold_grace`, `scoped`, `mirror`, `factor` относятся к сборке KAMI, не к `kami-patch` из этой папки.
* Остаётся мелочь: лёгкая «микротрясучка» камеры в покое (игра пытается вернуть наклон к горизонту, а
  `hold` ему сопротивляется).
* Общий приём: записать сценарий у препятствия (`camrec.py record --script idle:4,wall:12,idle:5`
  стиком и `wallm` мышью с KAMI), сравнить переходы слов-флагов в обоих (в записи со стиком их нет),
  затем проверить кандидатов командой `watch.py hold` и только потом переносить в `writes`.
* Другие режимы камеры (прицеливание, транспорт, лазание) могут быть другим объектом камеры: для
  них профиль снимается отдельно и включается условием `when`.

## Статический анализ (когда значение не «держится» или нужна логика игры)

В официальных сборках RPCS3 нет брейкпоинтов на запись в память, а обычные работают только в
интерпретаторе PPU. Поэтому вопрос «кто пишет в это поле» решается по исполняемому файлу.

1. Расшифруйте EBOOT: **Utilities → Decrypt PS3 Binaries** (или `rpcs3 --decrypt путь`).
2. Спросите у `ps3elf.py`:

```
py -3 ps3elf.py info      EBOOT.elf
py -3 ps3elf.py callers   EBOOT.elf --depth 4                    # кто читает геймпад и кто их вызывает
py -3 ps3elf.py fieldxref EBOOT.elf --offsets 0x1A8,0x1C4 --ops stfs --min-match 2
py -3 ps3elf.py dataxref  EBOOT.elf --addr 0x00785494            # кто ссылается на адрес (напр. множитель FOV)
py -3 ps3elf.py floats    EBOOT.elf                              # функции с константами углов
```

   Смещения для `fieldxref` - последние смещения цепочки (поля yaw и pitch внутри объекта камеры).
   Функция, которая **записывает** оба поля, - первый кандидат на код обновления камеры.
3. Проверьте кандидатов на живой игре. `fieldxref --bp-patch BCUS98119_patch.yml --hash PPU-...`
   пишет патч RPCS3, который при загрузке игры ставит брейкпоинт на каждую найденную запись.
   Положите файл в `patches`, включите его в **Manage → Game Patches**, переключите
   **PPU Decoder** на **Interpreter (static)**, откройте **View → Show Debugger** и поверните
   камеру: отладчик остановится на инструкции, которая реально пишет угол.
4. Если игра перезаписывает угол каждый кадр и мышь из-за этого не работает,
   `ps3elf.py patch EBOOT.elf --hash PPU-... --nop 0x... -o BCUS98119_patch.yml` делает патч,
   заменяющий эту инструкцию на `nop`. Запись через IPC на уже скомпилированный код не действует,
   поэтому такие правки делаются только патчем RPCS3.
5. Для чтения функций - Ghidra. Импортируйте `.elf` с языком `PowerPC:BE:64:A2ALT-32addr`,
   запустите `AnalyzePs3Binary` из [Ps3GhidraScripts](https://github.com/clienthax/Ps3GhidraScripts)
   до автоанализа. Скрипты из `ghidra_scripts` (категория KAMI в Script Manager):

   * `KamiFindFieldAccess` - то же, что `fieldxref`, но на границах функций Ghidra;
   * `KamiPadCallTree` - дерево вызывающих `cellPadGetData`;
   * `KamiImportFindings` - переносит находки `ps3elf.py --ghidra файл` в метки, комментарии и закладки;
   * `KamiExportDecompiled` - сохраняет декомпиляцию отмеченных функций в текстовые файлы.

`gdbtrace.py` делает шаг 3 автоматически и для каждого срабатывания печатает адрес, к которому
обращается инструкция. Он написан по исходникам GDB-заглушки RPCS3 и проверен только на её
имитации; после его отключения RPCS3 остаётся на паузе с ошибкой потока GDB Server в логе - это
особенность заглушки.

## Cheat Engine

`cheatengine/rpcs3_kami.lua` положите в папку `autorun` Cheat Engine. Появится меню KAMI:
подключение к rpcs3.exe, символ `ps3` (адрес можно писать как `ps3+00A12340`), типы с обратным
порядком байтов, диапазон сканирования, импорт `camfind.json` и `chains.json` в таблицу адресов
(записи по цепочкам сами следуют за объектом), экспорт таблицы. Вручную нужно один раз включить
**Settings → Scan Settings → MEM_MAPPED**. Указатели PS3 32-битные и с обратным порядком байтов,
поэтому сканер указателей самого Cheat Engine здесь не работает - используйте `ptrscan.py`.

## Что проверено, а что нет

Проверено автотестами (`tests/run_all.sh`, Linux) на симуляторе, который повторяет устройство
памяти RPCS3 и поведение его PINE-сервера по исходникам:

* весь путь `camfind → ptrscan → перезапуск → verify → mkprofile → управление как у KAMI` для трёх
  моделей камеры (два угла; пара sin/cos и угол; вектор направления), через процесс и через PINE;
* ручной режим `camfind` (робот выполняет подсказки);
* `ps3elf.py` на собранном тестовом исполняемом файле в формате PS3, кодировки инструкций сверены
  с `llvm-mc`;
* логика скрипта Cheat Engine под Lua 5.3 с имитацией его API;
* скрипты Ghidra скомпилированы против исходников Ghidra 12.1.4.

На Windows (`tests/test_camfind_win.py`, симулятор `tests/fake_rpcs3_win.py` - та же игра, но память
через `CreateFileMapping`/`MapViewOfFileEx` с двумя видами, как в RPCS3): `camfind` целиком, через
настоящие `ReadProcessMemory`/`WriteProcessMemory`/`VirtualQueryEx`, при этом игра подсовывает
NaN/inf/1e38 и 120 «двойников» угла в младших адресах. На настоящем RPCS3 проверены только чтение
(`watch.py info`, `selftest`) и запись «себя в себя» (`selftest --write`).

Не проверялось, потому что здесь это запустить негде:

* полный путь `camfind` на настоящем RPCS3 с настоящей игрой;
* `--stimulus vigem`;
* скрипты Ghidra и Cheat Engine внутри самих программ;
* `gdbtrace.py` на настоящей заглушке.

Симулятор - это модель, а не игра: в настоящей игре кандидатов будет на порядки больше, камера
может не стоять на месте в покое, а хранить ориентацию игра может иначе (например, кватернионом).
`camfind` в таком случае честно покажет, что «липких» значений нет, - тогда путь лежит через
статический анализ.
